# Spike: Ollama behaviour and model reality check

Run 2026-11-06 against the developer's existing `local-ai` pod: Ollama 0.40.14 (`ollama:rocm`), RX 6900 XT,
with `OLLAMA_NUM_PARALLEL=1` and `OLLAMA_KV_CACHE_TYPE=q8_0`. Only the API was used, with no configuration
changes. These are real measurements from this one machine on one day, using a small number of runs.

## Tool-loop test

The test offered one `read_file` tool and asked the model to read a file and report what it prints. The model
then received a tool result containing a string it couldn't have guessed.

- **L1:** it made a valid tool call.
- **L2:** it used the result correctly.

Three runs per model, `num_ctx=16384`, default thinking setting.

| Model | `tools` declared | L1 | L2 | Tok/s (generation) | Cold load | Memory (total / VRAM) | GPU layers |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `llama3.2:3b` | Yes | 3/3 | 3/3 | 140–147 | 4.8 s | 2.98 / 2.98 GiB | All |
| `qwen3:4b` | Yes | 3/3 | 3/3 | 110 | 1.5 s (recently cached) | 3.70 / 3.70 GiB | All |
| `gpt-oss:20b` | Yes | 3/3 | 3/3 | 92–94 | 30.1 s | 11.87 / 11.87 GiB | All |
| `qwen3.8:27b` | Yes | 3/3 | 3/3 | 11–29 | 42.4 s | 17.16 / 13.42 GiB | 54/66 |
| `qwen3.6:27b-coding` | Yes | 3/3 | 3/3 | 22–25 | 39.1 s | 16.98 / 13.52 GiB | 55/66 |
| `phi4-mini:latest` | Yes | **0/3** | 0/3 | 121 | 5.5 s | 3.55 / 3.55 GiB | All |
| `rocinante:12b` | Yes | **0/3** | 0/3 | 43–44 | 20.1 s | 10.31 / 10.31 GiB | All |
| `cydonia:24b` | Yes | **0/3** | 0/3 | 20–31 | 28.9 s | 13.83 / 13.83 GiB | All |

Not tested: `qwen3.8-heretic-ara`, `qwen3.8-cyber-redteam`, `gemma-4-12b-uncensored`, and `deephat:*` (no `tools`
capability declared).

### What this does and doesn't show

- **Declared capability is not enough.** All 8 models declare `tools`, and 3 of the 8 failed every run. This
  validates the probe design.
- **Failure modes differ.** Some models described the call in prose, asked for the file, or denied having access.
  One `cydonia:24b` run wrote what looks like a JSON tool call as text (`[{"n…`), so a dialect fallback might
  rescue it. This needs a follow-up test.
- **This is a low bar.** One tool and a trivial task. It says nothing about multi-step coding quality, which is
  what L3–L5 must test.
- **`qwen3:4b` thinks heavily.** It generated 800–1,100 tokens to make this one call, so its effective speed is far
  lower than the tok/s figure suggests. It took 2.6–2.9 s for the follow-up turn, versus 0.1 s for `llama3.2:3b`.
- **Memory depends on context.** Figures are at `num_ctx=16384`. Fit at 32k was not measured for these models.

**Candidate primary test model: `gpt-oss:20b`.** It's the largest model tested that stays fully on the GPU, and it
passed 3/3 at 92–94 tok/s. **`qwen3.6:27b-coding`** is the second candidate, and is noticeably slower because about
20% of it runs in system memory. Neither has yet been tested on real coding work.

## Ollama API behaviour

| Question | Result | Evidence |
| --- | --- | --- |
| Is an over-limit prompt rejected? | **No.** Silently truncated, with HTTP 200 and no error field. | Roughly 9,500 tokens of prompt (scaled from a measured sample) at `num_ctx=2048` gave `prompt_eval_count: 1026` |
| What gets dropped? | System prompt **kept**, oldest turns **dropped** (one run). | With a multi-turn history, the reasoning mentioned the system codeword but never the first-turn one |
| Can a near-full context produce nothing? | **Yes.** An empty reply with `done_reason: length`. | `prompt_eval_count: 1881` of 2048 left too little room after thinking |
| Does changing `num_ctx` reload? | **Yes.** Load time returned and the cache reset. | 4096 → 8192: `load_duration` 1.75 s, cached 12 → 0 |
| Does `/v1/chat/completions` honour `num_ctx`? | **No.** Both `options.num_ctx` and top-level were ignored, and the model reloaded at the server default. | Request 6000, `/api/ps` shows `context_length: 32768` |
| What does `prompt_eval_count` mean with a cache hit? | **The whole prompt.** Uncached = `prompt_eval_count − prompt_eval_cached_count`. | 3447 total, 3446 cached |
| What does the cache save? | A lot. | Same 3.4k-token prompt: 1.28 s, then 0.01 s |
| What does a changed prefix cost? | Everything after the change. | Changing the system message: cached 3445 → 5, back to 1.27 s |
| How do tool calls stream? | In one chunk in every passing run on this version. | `call_chunks: 1`. The adapter should still tolerate splitting, as the docs promise only "partial". |
| What does `think: false` do? | **Can leak reasoning into `content`** (`qwen3:4b`). No tool call came within 400 tokens. | Default thinking worked 3/3 on the same model |
| Are bytes sent during loading? | First chunk arrives after load, up to 53.9 s here. | Silence is normal, so this confirms a phase-aware watchdog |
| Is the context reported by the API? | Yes: `/api/ps` has `context_length`, `size` and `size_vram`. | Enables measured memory data |

## Memory versus context, `qwen3:4b`

Reported `size` from `/api/ps`, fully on GPU, with this server's `q8_0` KV cache setting:

| `num_ctx` | 2,048 | 4,096 | 8,192 | 16,384 | 32,768 |
| --- | --- | --- | --- | --- | --- |
| Size (GiB) | 2.55 | 2.70 | 3.08 | 3.70 | 4.97 |

That's close to linear, at about 0.08 GiB per 1,000 tokens of context, for this model and setting only.

## Other observations

- **`gpt-oss:20b` reports a loaded size (11.87 GiB) below its listed model size (12.8 GiB),** so listed size isn't
  a reliable lower bound. The estimator must be calibrated from measurements.
- **VRAM headroom:** the two 27B models settled with roughly 13.4–13.5 GiB in VRAM on a 15.98 GiB card, while about
  2 GiB was already used by the desktop.
- **Cold starts are a UX matter.** Up to about 54 s for the first chunk, so the loading state is essential.

## Not yet tested

Multi-step and real coding tasks, behaviour at 32k context for the large models, sustained speed with a long prompt,
concurrent use alongside Open WebUI, and dialect fallback for the models that failed.
